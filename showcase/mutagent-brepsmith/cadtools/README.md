# cadtools — deterministic CAD checkers for `mutagent-brepsmith`

The Python half of the `mutagent-brepsmith` agent. The agent itself is a Claude Code subagent
defined in [`../.claude/agents/mutagent-brepsmith.md`](../.claude/agents/mutagent-brepsmith.md);
these modules are the deterministic geometry code it calls over `Bash`. Nothing here asks a
model anything — that is the point. Verification is code, never a second opinion.

Specification (the source of truth): `agentspec.yaml` in the full MutagenT development
workspace (not shipped in this showcase — this folder is the minimal runnable agent).

## Bootstrap

```bash
uv sync --frozen        # reproduce the pinned toolchain (build123d / trimesh / manifold3d)
uv run pytest -q        # the full offline test suite
```

Python is pinned to 3.12 (`.python-version`); dependencies are locked in `uv.lock`.
The test suite is offline by construction: every fixture is generated by build123d code, and
the socket layer is closed for the duration of the run.

## CLI

Every subcommand prints one JSON object on stdout and uses its **exit code** as the gate.

```bash
uv run python -m cadtools.cli <subcommand> [options]
```

| Subcommand | What it does |
|---|---|
| `analyze` | Topology counts, surface-type histogram, bounding box, volume/area of a STEP file |
| `verify` | The validity gate. **Exits non-zero when the body is invalid** |
| `diff` | Localized-change diff between two bodies: distances, changed region, volume and Betti deltas, and the swept `cross_section`. `--expect-volume-delta <mm3>` / `--target-face-area <mm2>` (with `--tol`, `--change-axis`) turn intent into a failing check — extents alone cannot see a pad that swept the wrong cross-section |
| `score` | Benchmark-parity scorecard of a candidate against a ground truth |
| `grade` | Deterministic complexity tier (`low` / `mid` / `high`) |
| `gen-pairs` | Generate synthetic (input, instruction, ground-truth) triples (dev profile only) |
| `list-recipes` | List the available synthetic edit recipes and their edit types (dev profile only) |
| `fetch-dataset` | Download the public benchmark data and keep the editing samples |
| `round` | Claim the next edit→verify round. **Refuses round 6** |
| `emit` | Decide what to write as `output.step`. It always decides |
| `package` | Assemble the leaderboard submission zip (it never uploads) |
| `aggregate` | Roll per-sample scores into a run summary |

The `synthetic-pair-generator` capability is **not in this package**. It lives in a separate
distribution, `cadtools-devtools` (`devtools/cadtools_devtools/synthetic_pairs.py`), and an
eval profile does not install it.

The reason is an isolation failure, not tidiness. `RECIPES["thicken"].apply` **is** `_thicken`
and `generate_pair` exports exactly its output as `ground_truth.step`, so an eval subject that
can import the generator can recompute the answer key without ever opening a ground-truth
file — which is what five of twenty Arm-A samples did in `eval-run-001`. Shipping the checkers
and the generator in one wheel meant installing the tools a subject needs necessarily installed
the answer key into its own import namespace: there was nowhere to put a mechanical rule, only
somewhere to put a request.

Two install profiles:

```bash
uv pip install .                    # EVAL: runtime only. `import cadtools.synthetic_pairs`
                                    # and `import cadtools_devtools` both fail.
uv pip install -e . -e ./devtools   # DEV: both, for dataset authoring and the test suite.
```

`gen-pairs` and `list-recipes` remain registered CLI subcommands, and report a clean,
actionable error when the devtools distribution is absent. `scripts/check_isolation.py`
AST-audits a run's `round-*.py` scripts afterwards and **blocks aggregation** on any denied
import, answer-key path literal, or escape hatch it cannot statically clear.

## Run artifacts

Every run writes under `runs/` (relative paths only):

```text
runs/<run-id>/<sample-id>/
├── trace.jsonl     # append-only JSONL, one line per event
├── ledger.json     # round budget state
├── round-<n>.py    # the generated build123d script for each round
├── output.step     # the emitted candidate
└── report.json     # the final verification report
```

## Local scoring vs the leaderboard — read this before quoting a number

The local scorer emits **`cad_score_proxy`**, never `cad_score`. Two documented deviations:

1. **The interface axis is unavailable locally.** `interface_match` depends on keep-in /
   keep-out sub-volumes authored in the benchmark's private ground-truth repository. It is
   reported as `interface: null` with `interface_available: false`, and the proxy is
   renormalized over the remaining `0.6 + 0.1 = 0.7` of weight. The raw, un-renormalized
   weighted components travel alongside it so the gap is always visible.
2. **No ICP alignment; outputs are not canonically re-posed.** For the editing task the
   ground truth is a local change to `input.step` in the input's own coordinate frame, so
   re-posing would destroy the correspondence the metric depends on. Instead, frame
   agreement (bbox centre + extents) is a **hard failing check**: a mis-posed pair raises
   `FrameDisagreementError` rather than quietly scoring as a terrible edit.

Both comparison arms (`harness` and `baseline`) use the identical convention;
`aggregate.compare_arms` refuses to compare runs scored under different conventions.

## Spec-coverage gate

```bash
uv run python scripts/check_coverage.py
```

Asserts every `spec.capabilities.code[].id` has a module carrying `# @implements <id>` and a
test referencing it. This is the Python-adapted form of the shipped gate, which
collects TypeScript only.
